# Проверка вёрстки через Playwright MCP

Проверяет, что страница корректно рендерится на десктопном и мобильном вьюпорте.
Аргумент ($0) — URL или путь страницы (например `/dashboard` или `http://localhost:3001/dashboard`).
Если аргумент пустой — проверяются все страницы из списка ниже.

## Список страниц проекта

Публичные (без авторизации):
- `/` — главная
- `/login` — вход
- `/register` — регистрация
- `/about` — о проекте
- `/privacy` — политика конфиденциальности
- `/terms` — условия использования

Защищённые (требуют сессию — `JwtAuthGuard` + `proxy.ts`):
- `/dashboard` — главный экран
- `/expenses` — транзакции
- `/categories` — категории

Список страниц соответствует `apps/web/src/app/**/page.tsx`. Если появились новые
`page.tsx`, добавь их в этот список.

## Порядок действий

1. **Убедиться, что фронт запущен.** Проверить `curl -s -o /dev/null -w "%{http_code}"
   http://localhost:3001` (порт web — 3001, см. CLAUDE.md). Если не отвечает — поднять
   `npm run dev:web` в фоне и подождать старта (обычно 3–5 секунд).

2. **Определить список URL для проверки:**
   - Если `$0` задан — привести его к полному URL (`http://localhost:3001` + путь, если
     передан относительный путь).
   - Если `$0` пустой — взять весь список страниц выше (полные URL на `localhost:3001`).

3. **Для защищённых страниц** — если сессии нет, Playwright увидит редирект на `/login`.
   Это ожидаемо и не является багом вёрстки: зафиксируй это в отчёте отдельной строкой
   ("страница требует авторизации, проверена форма логина/редиректа"), не пытайся обойти
   авторизацию самостоятельно (учётных данных для входа у тебя нет — не изобретай их).
   Если пользователь заранее дал тестовые данные для входа в этом чате — можно один раз
   залогиниться через форму `/login` и переиспользовать сессию для остальных защищённых
   страниц в рамках этого запуска.

4. **На каждой странице через Playwright MCP:**
   - Установить desktop-вьюпорт (`1440x900`) через `browser_resize`, открыть страницу
     (`browser_navigate`), сделать снимок (`browser_snapshot` для структуры и
     `browser_take_screenshot` для картинки).
   - Установить mobile-вьюпорт (`375x812`, iPhone-like), перезагрузить/повторно открыть
     страницу, сделать те же снимки.
   - Проверить консоль на ошибки (`browser_console_messages`) — JS-ошибки рендера часто
     указывают на сломанную вёрстку до визуального осмотра.

5. **Проанализировать скриншоты и snapshot на типичные проблемы вёрстки:**
   - Горизонтальный скролл / вылезающий за экран контент на мобайле.
   - Перекрывающиеся элементы, обрезанный текст, не влезающие кнопки.
   - Пустые/сломанные блоки (не загрузившиеся изображения, пустые контейнеры там, где
     ожидается контент).
   - Разъехавшиеся отступы/сетка по сравнению с соседними страницами того же слоя (FSD:
     `views`/`widgets` должны быть визуально консистентны).

6. **Отчёт пользователю** — по каждой проверенной странице кратко: URL, статус
   (OK / есть проблемы), при проблемах — что именно и на каком вьюпорте (десктоп/мобайл),
   с приложенными скриншотами. Не создавай файлы отчётов — выводи текстом в чат.

## Важно

- Не фикси найденные проблемы вёрстки сам без запроса — это скилл проверки, а не
  исправления. Сообщи о находках и спроси, чинить ли.
- Не закрывай/не убивай процесс `npm run dev:web`, если это оказался уже запущенный сервер
  пользователя (проверяй, что подняли именно ты, прежде чем останавливать).
