# Expense Tracker

## What This Is

Персональный трекер расходов и доходов: пользователь регистрируется, входит в
систему и ведёт учёт своих финансовых операций (транзакций) по категориям.
Сейчас можно только просматривать — эта итерация добавляет полноценное
управление данными: создание, редактирование и удаление транзакций и
категорий, плюс отображение сводки баланса.

## Core Value

Пользователь может быстро зафиксировать доход или расход и увидеть,
сколько денег у него осталось.

## Requirements

### Validated

- ✓ Регистрация, вход и выход (JWT access + refresh с ротацией) — существующий код
- ✓ Просмотр последних 10 транзакций на `/dashboard` с пагинацией — существующий код
- ✓ CRUD категорий и транзакций реализован в API (`/api/categories`, `/api/transactions`),
  включая фильтры по периоду/типу/категории, пагинацию и агрегацию
  `GET /transactions/summary` — существующий код, фронт пока не использует запись/статистику
- ✓ Изоляция данных по пользователю (userId из JWT) — существующий код

### Active

- [ ] Пользователь может добавить транзакцию (доход или расход) — с /expenses и быстрым
      добавлением с дашборда
- [ ] Пользователь может отредактировать существующую транзакцию
- [ ] Пользователь может удалить транзакцию
- [ ] Страница `/expenses` показывает полный список транзакций (не заглушка)
- [ ] Пользователь может создать, отредактировать и удалить категорию
- [ ] Страница категорий работает как полноценный CRUD (не заглушка)
- [ ] Удаление категории с привязанными транзакциями блокируется с понятным
      сообщением (API уже отдаёт 409 — нужно отобразить на фронте)
- [ ] Пользователь видит сводку баланса/доходов/расходов за месяц (на основе
      существующего `GET /transactions/summary`)
- [ ] Пользователь видит разбивку доходов/расходов по категориям (простой
      список/таблица с цифрами, без графиков)

### Out of Scope

- Мультивалюта/конвертация — не нужна в этой версии
- Повторяющиеся транзакции (по расписанию) — отдельная задача на будущее
- Бюджеты/лимиты расходов по категориям — отдельная задача на будущее
- Экспорт/импорт данных (CSV/Excel) — отдельная задача на будущее
- Визуализация графиками (круговые/столбчатые диаграммы) — начинаем с
  простого табличного представления, графики можно добавить позже

## Context

Проект — монорепо на npm workspaces: `apps/web` (Next.js 16 App Router,
Feature Slice Design), `apps/api` (Nest 12, ESM), `packages/shared`
(Zod-схемы для auth/users). Категории и транзакции валидируются DTO-классами
на class-validator, а не Zod — контракт дублируется в
`packages/shared/src/schemas/category.ts`, но источник правды на фронте для
форм этих сущностей — локальные типы, а не `zodResolver`. У транзакций
Zod-дубликата нет вовсе, контракт ответа живёт в `transaction.types.ts`.

Модель `Transaction` — единая сущность доходов и расходов
(`TransactionType.INCOME`/`EXPENSE`), у категории нет привязки к типу —
любая категория подходит для любого типа транзакции. Деньги — `Decimal(12,2)`
в БД, строка в JSON; форматирование через `formatMoney`.

Известное расхождение имён: пункт меню «Транзакции» ведёт на `/expenses`
(сущность в api — `transaction`) — переименование не входит в задачу, это
техдолг, зафиксированный отдельно.

Полная карта кодовой базы (стек, архитектура, конвенции, тесты, интеграции,
техдолг) — в `.planning/codebase/`, актуализирована перед стартом этого проекта.

## Constraints

- **Tech stack**: Nest 12 (ESM) + Next.js 16 (App Router) + Prisma 7 + PostgreSQL —
  менять не планируется, работаем в рамках существующего стека
- **Валидация**: категории и транзакции — DTO-классы (class-validator) на бэке,
  а не Zod; при добавлении фронтовых форм для них следовать существующему
  паттерну (не `zodResolver`, как в auth)
- **FSD-слои**: фронт разложен по Feature Slice Design
  (`app → views → widgets → features → entities → shared`), кросс-импорты
  внутри слоя и между `entities` запрещены — склейку данных делает `widget`
- **Тесты**: раннер не настроен, тестов в проекте нет

## Key Decisions
