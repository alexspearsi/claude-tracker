# Phase 2 — UI Design Contract

> Visual and interaction contract for the transaction CRUD slice: `TransactionForm` (shared by
> `/dashboard` quick-add and `/expenses`), the `/expenses` list + filter panel, and the delete
> confirmation. Generated by gsd-ui-researcher, verified by gsd-ui-checker. This session ran in
> `--auto` mode: every open question left to "Claude's discretion" by 02-CONTEXT.md/02-RESEARCH.md
> was resolved here directly (reasoning inline below) rather than asked — no `AskUserQuestion` was
> used. This spec **extends** `01-UI-SPEC.md` (Phase 1) rather than re-deriving it — spacing,
> typography, color tokens and CTA-unification convention are inherited unchanged; only
> transaction-specific additions (type toggle, signed-amount color, filter panel, date picker) are
> new content below.

### Component Notes (this phase's discretion resolutions)

- **Type toggle (D-01 — "переключателем/табами, не select"):** two plain `Button`s
  (`variant={field.value === 'EXPENSE' ? 'default' : 'outline'}`), not `shadcn toggle-group` and
  not `shadcn tabs`. Resolves 02-RESEARCH.md Assumption A2 and follows the project's established
  bias (confirmed in Phase 1: plain `Button`s over `DropdownMenu` for row actions) toward zero new
  primitives when two existing `Button`s solve the requirement. `role="radiogroup"`,
  `aria-label="Тип транзакции"` on the wrapping `div`, per the exact sketch in 02-RESEARCH.md
  Pattern A.
- **Date-range filter shape (Claude's Discretion per CONTEXT.md):** a single `Calendar
  mode="range"` inside one `Popover`, not two separate single-date pickers — per 02-RESEARCH.md
  Open Question 1's own recommendation (fewer moving parts, the shadcn-documented pattern for date
  ranges). The trigger button shows the formatted range (`d MMM` – `d MMM`, `date-fns` `ru` locale)
  or "Период" placeholder when unset.
- **Quick-add trigger placement (Claude's Discretion per CONTEXT.md):** lives in
  `RecentTransactions`'s `CardHeader`, `flex justify-between` — identical treatment to
  `CategoryList`'s header (`CardTitle` + `Button` side by side, confirmed pattern read this
  session). `RecentTransactions` gains a `headerAction?: ReactNode` prop so the widget stays
  presentation-agnostic (it does not import `QuickAddTransaction` itself) — `DashboardView`
  passes `<QuickAddTransaction categories={...} />` into it.
- **Row actions on `/expenses`:** two plain ghost `Button`s ("Редактировать"/"Удалить"), same as
  `CategoryList` — no `dropdown-menu` (no precedent in this codebase, confirmed 02-RESEARCH.md).

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | "Добавить транзакцию" — used for **all three** entry points: the `/dashboard` quick-add trigger (`RecentTransactions` header), the `/expenses` page-header trigger, and the `/expenses` empty-state button (same unification rationale as Phase 1's D-07: one verb+noun across every entry point, not near-synonyms) |
| Dialog title — create | "Новая транзакция" (mirrors `CategoryForm`'s "Новая категория") |
| Dialog title — edit | "Изменить транзакцию" (mirrors `CategoryForm`'s "Изменить категорию") |
| Form submit — create | "Добавить" |
| Form submit — edit | "Сохранить" (mirrors `CategoryForm`'s create/edit submit-label split exactly) |
| Empty state heading (no transactions at all) | "Пока нет транзакций" (already the exact copy in `widgets/recent-transactions/ui/empty-state.tsx` — reused verbatim on `/expenses`, not restated differently) |
| Empty state body (no transactions at all) | "Добавьте первую транзакцию, чтобы увидеть её здесь" (already the exact copy in the existing `EmptyState` usage — reused verbatim) — followed by the "Добавить транзакцию" button |
| Empty state (filtered — zero results under active filters) | Heading: "Ничего не найдено" — Body: "Попробуйте изменить период, тип или категорию" — **no** CTA button here (unlike the true-empty state): adding a transaction doesn't fix "your filter excludes everything," it would be a non-sequitur action (see UI Considerations below) |
| Error state (list load failure) | "Не удалось загрузить транзакции: {message}" — exact structural mirror of `dashboard-view.tsx`'s existing pattern, reused for `/expenses` |
| Error state (field validation, inline) | Per-field message under the offending input via `FormMessage`, sourced from `extractFieldErrors()` — same as `CategoryForm` |
| Error state (toast — general mutation failure) | Whatever `apiErrorMessage()` returns as-is — no second copy layer, same rule as Phase 1 |
| Destructive confirmation (delete) | Title: "Удалить транзакцию?" — Body: "Это действие нельзя отменить." — Confirm button: "Удалить" (`variant="destructive"`) — Cancel button: "Отмена". **No item-name interpolation** (unlike `CategoryDeleteDialog`'s "Удалить категорию «{name}»?"): a transaction has no short human-readable name field — description is optional/free-text and can be empty, so the dialog states the action generically rather than risking an empty or truncated interpolated string; `AlertDialogDescription` may optionally show the transaction's amount + date as context (e.g. "−1 500 ₽ от 21 сентября") immediately below the title, at executor's discretion for extra confirmation clarity, but the title itself stays fixed copy |
| Filter panel — no active filter (date range trigger) | "Период" (placeholder, replaced by the formatted range once selected) |
| Filter panel — type select placeholder | "Тип" (placeholder for the type filter `Select`, distinct from the form's type toggle — this is a 3-state filter: "Все", "Доход", "Расход") |
| Filter panel — category select placeholder | "Категория" (placeholder; first option is "Все категории") |

**Rationale for the filtered-vs-true empty state split:** 02-CONTEXT.md's D-04 establishes the
filter panel as a first-class, always-visible surface on `/expenses` — this makes "zero results
because of an active filter" a distinct, expected state from "zero transactions ever created,"
and conflating their copy (either always showing the CTA, or never showing it) would mislead the
user in one of the two cases. This is new ground Phase 1 didn't need (categories have no filters).

Elements classified for this phase:
- `transaction-list` (`list-collection`) — the `/expenses` table (TXN-04)

- `transaction-delete-dialog` (`interactive-control`) — the `AlertDialog` (TXN-03)
- `transaction-filters` (`interactive-control`) — the filter panel (TXN-06)

|----------|------------|--------|---------------------|

| empty | transaction-list | ✅ covered | Filtered-empty (`total === 0`, ≥1 filter active) renders "Ничего не найдено" with no CTA, documented in `## Copywriting Contract` — distinguished from true-empty by checking whether any of `type`/`categoryId`/`dateFrom`/`dateTo` is present in `searchParams` |
| loading | transaction-list | ⚠ dismissed | `ExpensesView` is a Server Component (mirrors `DashboardView`); no custom `loading.tsx` this phase, consistent with the existing `/dashboard` pattern — project convention, not a phase-specific gap |
| loading | transaction-form | ✅ covered | Submit button shows `Loader2Icon` (spinning) and is `disabled` during `form.formState.isSubmitting` — exact pattern from `CategoryForm` |
| loading | transaction-delete-dialog | ✅ covered | `AlertDialogAction` shows `Loader2Icon` and is `disabled` during `isPending` — exact pattern from `CategoryDeleteDialog` |
| error | transaction-list | ✅ covered | "Не удалось загрузить транзакции: {message}" on `getTransactions()` failure; a 401 redirects to `/session-expired` before rendering — same as `/dashboard` |
| error | transaction-form | ✅ covered | Field-level via `extractFieldErrors()` → `form.setError()`; general via `apiErrorMessage()` toast — see `## Copywriting Contract` |
| error | transaction-delete-dialog | ✅ covered | No 409/blocked branch (Pitfall 3) — any error toasts and closes the dialog, no inline "keep dialog open" state exists for this entity |
| error | transaction-filters | ⚠ unresolved | A malformed `dateFrom`/`dateTo`/`type`/`categoryId` reaching the API (e.g. a hand-edited URL) would 400 with `forbidNonWhitelisted` — no specific inline recovery UI is specified here; planner should treat this as "falls through to the generic list error state" unless a more specific UX is designed during planning. Low risk per 02-RESEARCH.md Assumption A3 (loud, easy-to-catch 400, not silent corruption) |
| populated | transaction-list | ✅ covered | Table: date, description (or category name as fallback label when description is empty — see long-text row below), category dot+name, signed colored amount (D-03), "Редактировать"/"Удалить" row actions — mirrors `TransactionsTable` already shipped for `/dashboard` |
| partial | transaction-form | ✅ covered | Edit mode seeds `defaultValues` from a complete `Transaction` (all required fields always present per API contract); `description` may be `null`/absent — maps to an empty string field, not a placeholder-only-visible-on-partial-data case |
| overflow | transaction-list | ✅ covered | Pagination via `?page=` → `limit`/`offset`, existing `PaginationNav`/`totalPages` reused unchanged (TXN-04) — unlike categories, this is explicitly required this phase, not deferred |
| zero-one-many | transaction-list | ✅ covered | Zero → one of the two empty states above; one/many → same table row template, no singular/plural copy variance needed (page heading "Транзакции" is invariant) |
| long-text | transaction-list | 🧪 backstop | `description` is capped at 500 chars server-side (`DESCRIPTION_MAX`) but the table cell must `truncate` rather than wrap/break row height for a long description — held-out visual check, no automated test exists in this project (no test runner) |
| long-text | transaction-form | 🧪 backstop | The description `Input`/`Textarea` must not visually overflow its `Dialog` at 500 characters — rely on `w-full` sizing plus the schema's `.max(500)` cap; held-out visual check during manual UAT |
